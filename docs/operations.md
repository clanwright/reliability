# Operations

Local evaluation and disposable repositories test the executor. They do not
authorize repository initialization, real backup writes, maintenance, provider
lifecycle changes, or production restore. Each of those is a separate operator
action with destination-specific evidence.

The NixOS module entry point is `nixosModules.default`. Import a separate
recovery-unit contract producer, then set `clanwright.reliability.enable`,
`selectedUnits`, and named `destinations`. Each destination supplies a
credential-free `repository` and an absolute runtime `passwordFile`; optional
absolute `environmentFile` and `rcloneConfigFile` paths provide backend
credentials at runtime. The module does not import Primitives or Apps for you.
It rejects missing unit IDs and enables no maintenance by default. Capture is
network-isolated; if an owner-built handler needs to change local service
state while making a consistent copy, declare only its required host paths in
`captureWritablePaths` and verify its cleanup behavior independently. The
executor can terminate a capture process group on timeout or staging pressure;
the owner handler must trap termination and restore the prior application state.
Captured files and directories must be portable and contain no symlinks.
The staging monitor polls about every 50 ms, but its directory scan and process
termination also take time. A producer can exceed the configured staging size
or consume the remaining free space before it stops. Use a dedicated filesystem
quota when a strict disk bound is required; `maxStagingBytes` is a fail-closed
monitoring threshold, not a hard filesystem limit.

The flake pins nixpkgs by revision for its standalone package and local checks.
`local-ci` runs with Nix 2.35.2 from that pin. On Linux, the executor package,
NixOS module, and validator isolation check select the same Bubblewrap: they
use the consumer's `pkgs.bubblewrap` at version 0.13.0 or newer, otherwise a
small override using the official 0.13.0 release tarball. The module builds
from the consumer's `pkgs`, so a consumer's package set can differ from the
flake's pinned package set. Bubblewrap is not included on Darwin. To update
these dependencies, change the exact nixpkgs revision in `flake.nix`, run
`nix flake lock`, then run `nix run --no-write-lock-file .#local-ci`. Revisit
the Bubblewrap override when nixpkgs contains 0.13.0 or newer.

For Linux checks from macOS, configure the approved Linux Nix builder first,
then run:

```sh
nix build --no-write-lock-file --no-link .#checks.x86_64-linux.validator-isolation
nix build --no-write-lock-file --no-link .#checks.x86_64-linux.module-eval
```

The isolation check needs a Linux builder that supports unprivileged user
namespaces. These builds exercise local
test data and do not establish runtime acceptance with application handlers.

The installed executor accepts a JSON runtime config generated by the module.
The following examples use a disposable config and repository. Replace the
example path and destination only with an operator-approved environment:

```sh
nix run --no-write-lock-file .#local-ci
reliability --config /path/to/runtime-config.json capture
reliability --config /path/to/runtime-config.json backup archive-a
reliability --config /path/to/runtime-config.json check archive-a
reliability --config /path/to/runtime-config.json check archive-a --read-data
reliability --config /path/to/runtime-config.json restore-check archive-a
reliability --config /path/to/runtime-config.json status
reliability --config /path/to/runtime-config.json status --metrics-file /path/to/metrics/reliability.prom
```

`check --read-data` reads all repository data; the plain `check` performs a
structural check. `restore-check` restores the latest recorded complete
generation and runs each unit's owner-supplied validator in a network-isolated
`bubblewrap` environment. It requires a Linux host with the validator in the
Nix store and an unprivileged `reliability-validator` account. These commands
return bounded JSON status and record distinct evidence under the private state
directory. The validator receives read-only restored data at `/input` and
writable scratch at `/tmp`; it has no inherited environment or external network
access.
It must copy files into `/tmp` when import tools need to modify them.
The privileged-to-unprivileged handoff still requires a Linux runtime acceptance
test with the released application handlers.

The module schedules a capture every 12 hours, retries destination uploads
hourly, performs a structural check weekly, and schedules a full data read and
isolated restore check monthly. Its default warning and critical capture ages
are 18 and 24 hours. The retention policy defaults to a union of all snapshots
within 7 days, daily representatives within 1 month, weekly representatives
within 3 months, and monthly representatives within 1 year. These defaults
have no deletion effect until maintenance is commissioned and enabled. A status
service runs every five minutes. With optional absolute `metricsFile`, it
writes sanitized node-exporter textfile gauges for destination backup age and
severity; without that option, it reports JSON status to the journal. Missing
backup evidence is critical. External monitoring must also detect a dead host.

## Commissioning

1. Select stable unit IDs and verify the producer's capture, stored-format,
   and isolated validation contract. Record explicitly waived valuable state.
   Confirm that the matching Primitives and Apps releases, handler closures,
   configuration, and application/database versions are retained for recovery.
2. Provision independent encrypted repositories and runtime credentials for
   each destination. Keep recovery credentials and the application handler
   environment recoverable off the protected host. Record exact repository
   identities before enabling destructive maintenance.
3. Exercise capture and upload to each destination. A complete captured
   generation and a committed snapshot at one destination are separate facts.
   Reject partial or missing units and measure freshness from capture time.
   Each destination retries the newest complete local generation; older missed
   generations are not queued after a newer capture succeeds.
4. Read repository data and perform an isolated application restore and
   semantic validation from **each** destination. Test access after loss of the
   protected host. Preserve old repositories through migration.
5. Establish external stale-host alerting and observe independent destination
   evidence before accepting an installation. Successful local evaluation
   does not establish these runtime conditions.

## Routine verification

Track capture, upload, structural repository check, full data read, and
isolated semantic restore independently. A structural check cannot substitute
for a full read or application validation. Restore validation uses disposable
state with no production service paths, public ingress, or outgoing application
actions. Production restore requires its own runbook, compatible pinned
application handler, and explicit authorization.

## Maintenance

Automatic maintenance is disabled until separately commissioned. First record
a reviewed dry-run baseline for each exact repository identity and scope.
Commission each destination with its expected repository ID and the
`scopeFingerprint` returned
by the reviewed plan as `maintenancePolicyFingerprint`; the policy also requires
`maintenanceCommissioned`, a deletion ceiling, and a minimum surviving count.
For plan-only commissioning, set `policy.maintenanceEnabled = true`, leave
`policy.maintenanceCommissioned = false`, and set a positive deletion ceiling
and each destination's `expectedRepositoryId`. This permits a manual plan but
creates no maintenance service or timer. Review the plan and its removal count,
then set that destination's `maintenancePolicyFingerprint` and commission the
policy. Only then is weekly `maintenance-run` scheduled. Before any deletion,
require a fresh complete backup, fresh structural check, recent
semantic restore, unchanged policy fingerprint, acceptable deletion ceiling,
and minimum surviving recovery points for every lineage. A missing or retired
unit, empty selection, changed policy, or unexplained deletion plan stops the
operation for review. Retention in Restic does not set the provider's version
history lifecycle. Provider lifecycle changes require a repository-consistent
historical recovery drill and separate approval.

Maintenance also requires the local per-generation commit ledger to match the
exact remote snapshot IDs. An unresolved upload attempt or snapshot without a
matching commit blocks deletion. Preserve that ledger with the private state
directory; after losing the host or ledger, reconcile repository history
manually before maintenance can resume.

For a commissioned disposable repository, the executor's maintenance commands
are:

```sh
reliability --config /path/to/runtime-config.json maintenance-plan archive-a
reliability --config /path/to/runtime-config.json maintenance-apply archive-a
reliability --config /path/to/runtime-config.json maintenance-run archive-a
```

`maintenance-plan` records a bounded Restic dry-run result. An operator must
review that result and the configured deletion ceiling before applying it.
`maintenance-apply` requires a plan less than an hour old, rechecks the current
repository view, and stops if the planned removals changed. When removals are
planned, it forgets those snapshots and then prunes unreferenced repository
data. Once commissioned, the weekly timer uses `maintenance-run` to make a
fresh guarded plan and apply it in one operation. Neither command alters
provider object versions. A monthly full data read remains a separate check
from the weekly structural check. Never infer one from the other.
